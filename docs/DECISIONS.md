# Decisions

Settled. Don't re-litigate without new information; if you do reopen one, replace the entry rather than arguing alongside it.

## Architecture

- **No state-management library.** Off-mission; no component needs a global store. The fallback — extracting the subscription primitive `use-form` and `use-data-table` share — died on measurement: `use-data-table` is eight plain `useState` calls.
- **Composition is semantic, not universal.** A form field *is* a field, so `ui/form` uses `ui/field` and `ui/label`; a carousel arrow merely *looks like* a button and must not import `ui/button`. The test: would a consumer copying this one file be surprised by what came with it? Copy-paste independence is a real property being protected.
- **`FormItem` deliberately does not compose `Field`** — `Field` renders `role="group"`, and a group per form field changes the a11y tree.
- **Independent release windows, one monotonic `kitVersion`.** Per-component semver is refused: copy-paste has no escape hatch for the diamond problem.
- **No HTTP registry for the CLI.** `npx github:` already ships the whole tree.
- **`van.defaults.json` carries no `theme.brand`** — the kit palette is greyscale, so its 53 colour tokens are literal light/dark pairs.

## Component-level

- **The chip lives in `ui/badge` as `Chip`**, not its own slug.
- **Each `CSS.highlights` consumer gets its own registry name** — one global registry, so `ui/data-table` uses `vanillin-table-search`.
- **No `h1` pass.** No WCAG criterion requires one; "one `h1` per page" is best practice only, and fixing it would retarget every `h2` assertion in the suite.
- **`lib/use-color-scheme.js` owns no persistence and no DOM** — never writes `.dark`, never touches localStorage. An app already on `next-themes` does all three and a hook repeating them would fight it.
- **`ui/mode-toggle` is one rendering, an icon button.** Covering `<button aria-pressed>`, `role="switch"` and `<input type=checkbox>` in one component would force importing `ui/button` + `ui/switch` + `ui/checkbox`, so every consumer copying one file would get three components and render one. A switch or checkbox is a two-line consumer composition over `useColorScheme()`, shown on the demo page. Do not add a `variant` prop for it.

## Motion

- **The page-wide light/dark sweep is gone. Don't bring it back casually.** The mode toggle swaps the scheme instantly and keeps its feedback inside the button. The `clipPath` option survives in `lib/view-transition.js` and is demonstrated on the View Transitions page, where a wipe is the subject rather than a side effect.
- **A feathered view-transition edge is not buildable in Chrome.** `mask-image` is ignored on view-transition pseudo-elements — probed twice, through WAAPI and as a static rule. It produces a flawless animation object and paints nothing.
- **The Chromium-only `overlay` transition stays, and its exit polish is accepted as per-engine.** Seven components (`popover`, `select`, `dropdown-menu`, `tooltip`, `hover-card`, `combobox`, `navigation-menu`) name `overlay … allow-discrete` so the panel survives its exit animation in the top layer. Safari and Firefox do not implement it and drop the panel the instant `hidePopover()` runs, so exits clip. The alternative — holding panels alive through exit via `lib/use-presence.js` and a delayed `hidePopover` — is real work across all seven, and **there is no WebKit in this suite to validate it against** (task122). Building an exit-timing fix with no engine to measure it on is how the mask-image and easing entries above were earned. Revisit once task122 lands WebKit in CI; not before.
- **A viewport-sized reveal has a viewport-sized feel, and there is no single timing for every display.** Four easings were tried; none read correctly on a 14" 120Hz laptop and a 27" 60Hz display at once. Feedback whose size is fixed — inside the control — does not have this problem.

## Docs and naming

- **The `docs/ISSUES.md` rename is deliberately half done.** The file and every reference point at it, but item ids (`A2`, `C5`, `E1`…) and the task slug `task68-bug-batch` are untouched — **these are going onto real GitHub issues later**, so renaming ids now would be churn twice over.
- **shadcn is named only on the introduction page.** Everywhere else says "upstream".
- **The `van` rename is done** — `van.config.json`, `styles/van.css`, `/* Generated by van */`. Deliberately *not* renamed: the package name, the `vanillin:resizable:*` localStorage key, the `vanillin-search` highlight key, and docs-site prose.

## Browser floor

- **`light-dark()` is a hard requirement, and the floor is accepted rather than softened.** All 47 colour tokens in the generated `styles/defaults.css` are bare `light-dark()` with no preceding plain declaration, so anything below Firefox 120 (ESR 115 included) or Safari 17.5 gets no colours at all — a hard failure, not a degradation. (Firefox 125–127 render colours correctly and lose only `@property` token *interpolation*; the two limits are often conflated.) The considered alternative was emitting a plain light-value line before each `light-dark()` from the generator: it is mechanical, but it doubles the token block for every consumer and buys back only *light* mode, since dark would then need the `.dark`-class JS path on exactly those old engines. Nobody has asked for ESR support. Reopen this with a consumer request, not on principle. `styles/globals.css` carries an `@supports not (color: light-dark(…))` rule that sets `--vanillin-unsupported: "light-dark"` on `:root` — a diagnosis, deliberately not a repair.
- **Dark mode is root-only.** `.dark` belongs on `<html>`. A scoped `<div class="dark">` half-works and is not supported: `color-scheme` does flip on the subtree, but every registered colour token was already computed against the root's light scheme and inherits *resolved*, so descendants get light colours with dark-styled form controls. Measured in `tests/tokens.test.mjs`, which pins both halves. `ui/button`, `ui/input-group` and `ui/native-select` still carry `.dark X` descendant rules implying subtree support; re-aiming those is tracked in #57.
- **`@property` with `syntax: "*"` is not a fallback guarantee.** Measured: a universal-syntax token reads back empty once invalid, and every declaration using it goes invalid-at-computed-value-time, so an inherited value wins and `initial-value` is never reached. A typed registration (`<color>`, `<length>`) does fall back correctly. The three `--typeset-font-*` registrations are therefore decorative today; the repair is a `var()` fallback at each consumption site, tracked in #56.
