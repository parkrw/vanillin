# Decisions

Settled. Don't re-litigate without new information; if you do reopen one, replace the entry rather than arguing alongside it.

## Architecture

- **No state-management library.** Off-mission; no component needs a global store. The fallback — extracting the subscription primitive `use-form` and `use-data-table` share — died on measurement: `use-data-table` is eight plain `useState` calls.
- **Composition is semantic, not universal.** A form field *is* a field, so `ui/form` uses `ui/field` and `ui/label`; a carousel arrow merely *looks like* a button and must not import `ui/button`. The test: would a consumer copying this one file be surprised by what came with it? Copy-paste independence is a real property being protected.
- **`FormItem` deliberately does not compose `Field`** — `Field` renders `role="group"`, and a group per form field changes the a11y tree.
- **Independent release windows, one monotonic `kitVersion`.** Per-component semver is refused: copy-paste has no escape hatch for the diamond problem.
- **No HTTP registry for the CLI.** `npx github:` already ships the whole tree.
- **`van.defaults.json` carries no `theme.brand`** — the kit palette is greyscale, so its 53 colour tokens are literal light/dark pairs.

## Component-level

- **The chip lives in `ui/badge` as `Chip`**, not its own slug.
- **Each `CSS.highlights` consumer gets its own registry name** — one global registry, so `ui/data-table` uses `vanillin-table-search`.
- **No `h1` pass.** No WCAG criterion requires one; "one `h1` per page" is best practice only, and fixing it would retarget every `h2` assertion in the suite.
- **`lib/use-color-scheme.js` owns no persistence and no DOM** — never writes `.dark`, never touches localStorage. An app already on `next-themes` does all three and a hook repeating them would fight it.
- **`ui/chart` draws its own SVG under the Recharts names, cartesian first.** The kit has no runtime dependency but React, so upstream's Recharts half is written here: `BarChart`/`LineChart`/`AreaChart`, `Bar`/`Line`/`Area`, `XAxis`/`YAxis`, `CartesianGrid`, `LabelList`, over pure math in `lib/chart-math.js`. The names are Recharts' so upstream's cartesian examples paste in unchanged; the shell (`ChartContainer`, `ChartTooltipContent`, `ChartLegendContent`) is upstream's verbatim. Pie, radar and radial (#85) share the shell and sit on a second root, `PolarChart`, beside `CartesianChart`: polar scales and arc paths share nothing with the cartesian layout but the pure helpers, and the active index is a slice, a spoke or a ring rather than a band. Angles are Recharts' (degrees, 0° at 3 o'clock, counter-clockwise), and a full circle is two half arcs because one 360° arc is degenerate in SVG. No entrance animation, no RTL axis mirroring, no `Brush`. `syncId` shares the active index between charts through a module-level channel, by position (Recharts' `syncMethod="index"`); a synced chart takes the index without the pointer's point, which is in the other chart's coordinates. Reference marks (`ReferenceLine`, `ReferenceArea`, `ReferenceDot`) resolve through the layout's scales, so they need no axis knowledge of their own.
- **`ChartStyle` emits `theme: { light, dark }` as one `light-dark()` value in a single `[data-chart=id]` rule, never upstream's `.dark [data-chart]` selector.** Dark mode is root-only here (Browser floor, below): colour tokens resolve at the root's `color-scheme`, so a `.dark` selector would only ever match the same root and is the wrong mechanism, and `light-dark()` is already the kit's hard floor. Input is sanitised on the way into `innerHTML`: keys must match `[\w-]+`, values containing `<`, `{`, `}` or `;` are dropped.
- **The chart palette is tuned to 1.4.11, not taken from upstream.** shadcn's `--chart-1…5` are a vivid P3 set: light `--chart-4`/`--chart-5` sat at 1.72:1 and 2.13:1 on white and dark `--chart-1` at 2.90:1 on the page. The hue angles stay and only lightness and chroma move: gold `--chart-4` at L 0.66 (3.15:1), amber `--chart-5` at L 0.57 (4.58:1), dark blue `--chart-1` at L 0.56 (3.99:1, 3.61:1 on `--card`). Against white every 3:1 colour sits at OKLab L ≤ ~0.67, so two warm hues 14° apart at that ceiling read as one series; amber goes darker instead, ΔE 0.097 from gold (0.074 upstream). All three are in sRGB, so the probe measures what is painted rather than a clipped P3 value. Legend and tooltip text still name each series, but they no longer stand in for a fill's contrast.
- **`ui/sparkline` is its own slug over `lib/chart-math.js`, not a `ui/chart` primitive, and is always `aria-hidden`.** It takes a series, or a few on one shared scale (`series`), and draws each as a stroke, a wash and the latest point in a fixed box: no `ChartContainer`, no config, no tooltip, no axes. Colour comes from props named for the part they paint (`color`/`theme` as a chart series takes them, `dotColor`, `areaColor`, `areaOpacity`), each set inline as `color` or a `--sparkline-*` property only when passed, so an ancestor's CSS still reaches the parts a prop leaves alone; React's style object needs none of `ChartStyle`'s sanitising because nothing goes through `innerHTML`. A series item with no colour takes `--chart-1…5` by position, as a chart series does. A trend line that needed any of those would be a chart, and a consumer copying one file for a stat card should not receive the chart shell with it. The two share `pointScale`/`linearScale`/`linePath`/`areaPath`, so a series is drawn the same way at either size. There is no accessible-name path because the figure it illustrates is always the text beside it; naming the svg would read the same number twice, and a sparkline with no number beside it is a misuse the API does not cater for. `thresholds` bands the line by value, each stretch and its wash in the zone it sits in, through one `userSpaceOnUse` gradient with hard stops, rather than switching the whole line on the latest value: a past spike stays red, and the dot carries the current zone. The amber band is `--warning` swung to hue 92, because the token's own orange reads too close to the red band at 1.5px; light sets it to L 0.62, since lifted it was 1.58:1 on a white card and the band is the information, and dark lifts it 0.1, where the raw token already clears 10:1. Descending thresholds read lower-is-worse, so a free-space or success-rate meter is the same prop. A sample that is not a finite number is a gap, not a reading: drawn at the baseline it reads as zero, and a NaN in the path data truncates the line, so the line and wash break there and the dot marks the latest reading. The domain folds 0 in on either side, so a negative series keeps its baseline, and a value past `min`/`max` pegs to that edge as a gauge does rather than leaving the box. `scale="log"` has no zero, so an unset or non-positive end falls back to the positive readings and a reading at or below zero pegs to the floor, where d3 returns `NaN` and the path would truncate. `times` is an array beside `points`, not `[t, v]` pairs, so `points` keeps one shape.

A time-range picker is composed beside the sparkline, not a prop on it: the svg is `aria-hidden` and holds no state, a menu inside would pull `ui/dropdown-menu` into every stat card, and each range is its own query at its own resolution, not a slice of a year the component was handed. The toggles live beside it for the same reasons as the range picker.
- **`natural` and `basis` curve types alias `monotone`.** Both are smooth splines that overshoot between data points; Fritsch–Carlson monotone-X never does, which for a chart of measurements is the property that matters. Accepting the names keeps upstream examples pasting; drawing them differently would add two interpolators for a difference no reader of the chart is meant to notice.
- **`ui/mode-toggle` is one rendering, an icon button.** Covering `<button aria-pressed>`, `role="switch"` and `<input type=checkbox>` in one component would force importing `ui/button` + `ui/switch` + `ui/checkbox`, so every consumer copying one file would get three components and render one. A switch or checkbox is a two-line consumer composition over `useColorScheme()`, shown on the demo page. Do not add a `variant` prop for it.

## lib/

- **`useControllableState` reports a same-value set in controlled mode — a deliberate divergence from Radix.** Radix guards the controlled branch with `if (value !== prop)` and stays silent; verified in `radix-ui/primitives` at `3635c2520f66` (2026-07-15) and at `5d036b592890`, before the radix-ui/primitives#3455 rewrite, so neither 1.x nor the `caller` rewrite fires. We drop the guard because a controlled parent that rejected a change still holds the old value, so swallowing the repeat makes the user's second identical choice unreachable; whether a value is a no-op is the parent's call. The uncontrolled branch keeps its `Object.is` guard, as Radix's does. Pinned in `tests/use-controllable-state.test.mjs`.
- **`formatDuration` defaults to `engine: "portable"`.** `Intl.DurationFormat` is a per-runtime probe — Node 22 has it, many browsers do not — so defaulting to it made a server and the browser hydrating its output word the same duration differently. Composing `Intl.NumberFormat` + `Intl.ListFormat` unconditionally is the only default both sides agree on. This changed public output after `v0.1.0`, which used `Intl.DurationFormat` wherever it existed; `engine: "auto"` restores that, and the first `CHANGELOG.md` entry (#26) must name both. Rejected: defaulting to `"auto"` until a CHANGELOG exists — it keeps the hydration mismatch as the default for the SSR case the CLI targets.

## Motion

- **The page-wide light/dark sweep is gone. Don't bring it back casually.** The mode toggle swaps the scheme instantly and keeps its feedback inside the button. The `clipPath` option survives in `lib/view-transition.js` and is demonstrated on the View Transitions page, where a wipe is the subject rather than a side effect.
- **A feathered view-transition edge is not buildable in Chrome.** `mask-image` is ignored on view-transition pseudo-elements — probed twice, through WAAPI and as a static rule. It produces a flawless animation object and paints nothing.
- **The Chromium-only `overlay` transition stays, and its exit polish is accepted as per-engine.** Seven components (`popover`, `select`, `dropdown-menu`, `tooltip`, `hover-card`, `combobox`, `navigation-menu`) name `overlay … allow-discrete` so the panel survives its exit animation in the top layer. Safari and Firefox do not implement it and drop the panel the instant `hidePopover()` runs, so exits clip. The alternative — holding panels alive through exit via `lib/use-presence.js` and a delayed `hidePopover` — is real work across all seven, and **there is no WebKit in this suite to validate it against** (task122). Building an exit-timing fix with no engine to measure it on is how the mask-image and easing entries above were earned. Revisit once task122 lands WebKit in CI; not before.
- **A viewport-sized reveal has a viewport-sized feel, and there is no single timing for every display.** Four easings were tried; none read correctly on a 14" 120Hz laptop and a 27" 60Hz display at once. Feedback whose size is fixed — inside the control — does not have this problem.

## Docs and naming

- **The `docs/ISSUES.md` rename is deliberately half done.** The file and every reference point at it, but item ids (`A2`, `C5`, `E1`…) and the task slug `task68-bug-batch` are untouched — **these are going onto real GitHub issues later**, so renaming ids now would be churn twice over.
- **shadcn is named only on the introduction page.** Everywhere else says "upstream".
- **The `van` rename is done** — `van.config.json`, `styles/van.css`, `/* Generated by van */`. Deliberately *not* renamed: the package name, the `vanillin:resizable:*` localStorage key, the `vanillin-search` highlight key, and docs-site prose.

## Browser floor

- **`light-dark()` is a hard requirement, and the floor is accepted rather than softened.** All 47 colour tokens in the generated `styles/defaults.css` are bare `light-dark()` with no preceding plain declaration, so anything below Firefox 120 (ESR 115 included) or Safari 17.5 gets no colours at all — a hard failure, not a degradation. (Firefox 125–127 render colours correctly and lose only `@property` token *interpolation*; the two limits are often conflated.) The considered alternative was emitting a plain light-value line before each `light-dark()` from the generator: it is mechanical, but it doubles the token block for every consumer and buys back only *light* mode, since dark would then need the `.dark`-class JS path on exactly those old engines. Nobody has asked for ESR support. Reopen this with a consumer request, not on principle. `styles/globals.css` carries an `@supports not (color: light-dark(…))` rule that sets `--vanillin-unsupported: "light-dark"` on `:root` — a diagnosis, deliberately not a repair.
- **Dark mode is root-only.** `.dark` belongs on `<html>`. A scoped `<div class="dark">` half-works and is not supported: `color-scheme` does flip on the subtree, but every registered colour token was already computed against the root's light scheme and inherits *resolved*, so descendants get light colours with dark-styled form controls. Measured in `tests/tokens.test.mjs`, which pins both halves. Dark-only descendant rules are written `:where(html).dark X` so they cannot match a scoped wrapper; `tests/tokens.test.mjs` pins that for `.btn--outline`.
- **`@property` with `syntax: "*"` is not a fallback guarantee.** Measured: a universal-syntax token reads back empty once invalid, and every declaration using it goes invalid-at-computed-value-time, so an inherited value wins and `initial-value` is never reached. A typed registration (`<color>`, `<length>`) does fall back correctly. The three `--typeset-font-*` registrations stay because they document intent and cost nothing, but the guarantee comes from a `var()` fallback at each consumption site.
